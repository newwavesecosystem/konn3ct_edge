**New incident:** a participant intermittently hears their own voice, especially when another person joins or leaves. This can have several mechanisms. Direct playback of the local microphone, SFU routing of an owned producer back to its originating session, another person’s microphone returning speaker output, another device/tab in the same room, and screen/system audio returning the meeting mix must be distinguished. The join/leave timing is evidence to investigate; it does not establish one mechanism by itself.

**A15 · High — local capture can become eligible for remote playback after roster identity corruption.**

The code path is concrete:

1. The local participant row contains `audioTrack`, holding the local microphone or its processed output.
2. The previously identified A02 bug classifies a duplicate remote user as local. It mutates the local row’s `id`, `userId` and role, while retaining the local `audioTrack`.
3. On the next state calculation, the `currentUser` selector can no longer find that row under the actual local identifiers and falls back to `initialCurrentUser`.
4. `GlobalAudioRenderer` uses the resolved current-user ID to exclude local rows. The corrupted row now looks remote, so its retained microphone is assigned to a playback slot.
5. The slot passes `isLocal={false}` to `AudioRenderer`. That renderer attaches the track to a `MediaStream`, calls `play()`, and renders an unmuted audio element when output volume is nonzero.

Source: [current-user selection](https://github.com/sirkays/konn3ct-test/blob/67780bdf0f3e4ad206ad0bc32183cee6fac168d4/frontend/lib/meeting-context.tsx#L497-L507), [roster reconciliation](https://github.com/sirkays/konn3ct-test/blob/67780bdf0f3e4ad206ad0bc32183cee6fac168d4/frontend/lib/meeting-context.tsx#L2104-L2273), [slot assignment and rendering](https://github.com/sirkays/konn3ct-test/blob/67780bdf0f3e4ad206ad0bc32183cee6fac168d4/frontend/lib/meeting-context.tsx#L3414-L3551), and [playback attachment](https://github.com/sirkays/konn3ct-test/blob/67780bdf0f3e4ad206ad0bc32183cee6fac168d4/frontend/lib/meeting-context.tsx#L3554-L3660).

**Reproduction E01:** the actual source-extracted roster callback, current-user selector, global renderer and audio renderer were executed in sequence. A synthetic enabled local microphone survived under a remote ID, was passed as non-local, and reached `play()` with `muted=false`. Browser playback, React scheduling and media tracks were mocked; this proves the application routing defect, not the acoustic output or frequency of the reported production incidents. E00 confirmed that an ordinary correctly identified local row is excluded.

Join/leave events trigger roster and slot changes; the server also schedules authoritative roster broadcasts. This creates opportunities for the defect to surface when duplicate or transitioning identities exist. A01’s deletion of self on a remote leave does not, by itself, prove self-audio. Do not equate every departure with a reproduced audible echo.

**A16 · High defense gap — playback trusts slot allocation and inconsistent identity filters.**

The microphone pool excludes self during a parent `useEffect`, but the actual JSX render looks up the slot’s participant and unconditionally passes `isLocal={false}`. E02 established that an existing slot can hand the now-local row’s track to the child during an identity transition before the parent reconciliation effect clears the slot. Whether that becomes audible, and for how long, depends on browser/React timing that was not measured here. Local-source exclusion must be enforced at the final playback boundary as well as during allocation.

Screen audio has a weaker filter: it checks only `p.id !== currentUserId`, whereas microphone allocation also checks `p.userId`. E03 reproduced that inconsistency in a synthetic transition state. This does not establish that ordinary local screen capture is stored in `screenAudioTrack`; it demonstrates a boundary that is insufficient if such a self-owned track arrives through stale or mismatched state.

The repair should use stable session ownership and explicit track provenance. Local raw microphone, processed microphone, their tracked clones and locally captured screen audio must not become remote playback merely because a row’s ID changes. Do not rely on `track.id` alone: processed and cloned tracks can differ. Associate media with owner session, source, producer/consumer and generation. Do not suppress all devices sharing an account without defining the intended multi-device policy.

**Existing protections and unproven alternatives.**

| Area | What source establishes | What remains to verify |
|---|---|---|
| SFU self-consumption | The client already skips producers whose participant ID equals its current participant ID. The server rejects a matching owner with `SELF_CONSUME_NOT_ALLOWED`; producer discovery also excludes current self. | Behavior for stale/replaced sessions, missing metadata and outdated producer ownership. These safeguards cannot stop direct local playback inside the browser. |
| Acoustic echo cancellation | `enableMic` and the AI-noise-suppression reacquisition path already request `echoCancellation: true`. | Actual raw-track settings, device/browser support, speaker placement, processing paths and whether another participant returns the sound. Adding the same flag is not a complete repair. |
| Screen/system audio | `getDisplayMedia` requests `audio: true` and creates a separate `screen-audio` producer when audio is supplied. | Whether a shared tab/window/system source includes meeting output and sends it back to its original speaker. Preserve intentional presentation/eCinema audio. |
| Duplicate consumers | The earlier audit reproduced duplicate subscription creation. | Duplicate consumers do not automatically prove duplicate audible outputs: establish which tracks actually reach which playback elements. |
| Recorder | Recorder mode explicitly refuses microphone acquisition in `enableMic`. | Verify that the actual recorder mode is selected and remains receive-only through reconnects. A recorder departure can trigger roster defects without the recorder sending echo. |

Browser guidance: requesting a boolean echo-cancellation constraint does not guarantee a particular effective capture setting; inspect supported constraints and the actual capture track. See [MDN echoCancellation](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackConstraints/echoCancellation). Screen-capture source choices and audio availability vary by browser and operating system; options such as self-browser-surface and system-audio hints need compatibility checks. See [MDN getDisplayMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia). Neither browser constraint is a substitute for correct application ownership checks.

**Incident 4 acceptance and diagnosis.**

| Scenario | Required evidence |
|---|---|
| Normal meeting and roster churn | Three independent participants A/B/C; A and B use distinct controlled audio sources. Repeated C join/leave, duplicate roster entries and stale snapshots must never route A’s local capture into A’s remote playback. Verify other participants still hear A. |
| Identity/slot transition | Existing warm slot, corrected local identity, participant ID changes and more than eight audio sources. Self exclusion must hold in every rendered state, before reconciliation effects settle. |
| Source lifecycle | Raw/processed mic replacement, AI suppression changes, mic device changes, producer replacement and delayed closes. One intended remote output per source; no old track or owned local clone in the remote pool. |
| Acoustic versus application path | Repeat first with headsets or isolated devices, then with controlled speakerphone use. Correlate returned sound with individual peer microphone/consumer muting and producer ownership. A headset test alone does not prove all echo is fixed. |
| Screen/system audio | Presentation tab audio, sharing a meeting-containing surface, supported system audio and screen-share stop/restart. Preserve legitimate shared content while identifying any returning meeting mix. |
| Recorder and recovery | Recording off/on/start/stop/restart; signaling reconnect, media restart, hard reload, temporary network impairment and same-account multiple devices. Verify recorder mode remains receive-only. |
| Duration and output | Continuous recording beyond the observed two-hour boundary; four hours remains a proposed diagnostic duration. Capture per-output routing and controlled source-return evidence, not only DOM counts or “connected” labels. |

For a live incident, collect a common UTC timeline, pseudonymous participant/session/generation IDs, local capture lineage, remote producer/consumer ownership, slot-to-track mapping, audio-element mute/volume/play state and selected output device category. Record whether the affected person was wearing a headset, whether a second device/tab was present, and whether screen/system audio was active. Use controlled test audio for content-level comparisons; do not log private meeting audio, bearer credentials or personal identifiers by default.
