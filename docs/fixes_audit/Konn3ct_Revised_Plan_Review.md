**Konn3ct revised implementation plan — review and required corrections**

Reviewed 16 September 2026. Input: `Pasted markdown(1).md`, titled “Konn3ct Reliability Engineering Implementation Plan: Incidents 1, 2, 3, and 4.”

**Assessment: the plan now covers all four incidents and incorporates several important corrections, but it needs the bounded amendments below before implementation follows it literally.** Continue implementation after integrating these amendments into the existing plan. Production acceptance must depend on the resulting diff and executed tests.

The improvements include typed resume results through the media-controller interfaces, generic request error settlement, microphone identities in both participant-creation paths, per-track playback errors, explicit self-audio defenses, early socket-message buffering, atomic role updates and recording/network test scenarios. These are useful changes in direction; they are not yet evidence of a completed repair.

This review compared the plan with the previously audited source at `67780bdf0f3e4ad206ad0bc32183cee6fac168d4`. Antigravity’s dirty local edits and untracked `src/routes/kv4.ts` have not been supplied here. Source identifiers described as missing below refer to that audited baseline; Antigravity should show any local definitions or implementations that resolve them. No application source was edited and no new runtime tests were performed for this plan review.

**Seven required corrections**

| Ref | Finding in the revised plan | Required correction and acceptance evidence |
|---|---|---|
| R1 — Protect healthy media | Component 2 says that a failed resume should “clean up local consumer and transport.” The client uses a shared receive transport. Closing it can terminate every consumer on that transport. | Clean up only the failed client/server consumer, its metadata and retry state. Rebuild the transport only when transport-level failure is established, using the recovery supervisor. With three speakers and one injected resume failure, the healthy consumers must remain open and audible. |
| R2 — Use consistent keys and complete async contracts | In-flight work is stored under `producerId:transportId`, but reconciliation checks `.has(producerId)`. The resume example still uses an undeclared `requestId`. Request resolution accepts any success message with a matching ID. Reject cancelled promises, cancel queues/backoff and fence continuations. Add concurrent-consume, stale-response and leave-during-retry tests. |
| R3 — Make the self-audio guard implementable and reactive | The local-track registry is only a snapshot of IDs. **Why R1 is urgent.** A selective speaker failure must stay confined to that subscription. The repository creates a single `recvTransport` and consumes multiple streams on it. The [mediasoup client API](https://mediasoup.org/documentation/v3/mediasoup-client/api/#transport-close) documents that closing a transport closes its associated producers and consumers. Implementing the plan’s cleanup sentence literally could expand one missing speaker into loss of all received audio/video.

**Additional implementation details to include in the same correction pass**

- **Consumer-close payload:** the existing callback is `onConsumerClosed(producerId, appData)`. It does not supply a `consumerId` positional variable. If cleanup uses consumer ID, update the typed event and all emitters/callers. Require nonempty ID matches plus ownership/generation checks. Comparing two missing IDs must never match and clear unrelated participants.
- **Playback-error state:** update the `Set` immutably so React observes changes. Track slot/track assignment generation, not only a reusable track ID, so a stale success or cleanup cannot remove a newer failure. Combine local-source rejection and volume policy into consistent element mute/attachment behavior.
- **Distributed resume:** the baseline media RPC dispatcher already serializes the controller’s returned `result`. Verify that typed results survive this existing boundary; edit it only if necessary. Convert both returned failure outcomes and thrown RPC errors/timeouts into correlated signaling failures. Validate old-media/new-signaling behavior rather than assuming a non-undefined result.
- **Source-identity policy:** the plan’s broad account/user matching needs explicit multi-device rules. A second device owned by the same account is not necessarily the same local capture session. Preserve supported multi-device behavior while blocking this session’s own capture and stale owned producers.
- **Production hypotheses:** retain checks for acoustic echo, another tab/device, screen/system audio, actual recorder mode and actual local/upstream join behavior. The reproduced direct-playback path is important, but it does not establish the cause of every incident.

**Accuracy corrections in the plan**

The Incident 4 summary says a remote departure or duplicate entry causes roster mutation. The reproduced mutation requires the duplicate/misclassified roster condition; a departure alone was not proven to cause it. Join/leave churn can expose the condition. The summary also says microphone slots use `isLocalIdentifier`; the audited slot-allocation function actually compares `p.id` and `p.userId` with `currentUserId`. These should be described accurately so the repair is based on actual code.

The “Host Authorization Hardening” box says insecure elevation “is permanently eliminated.” This is a proposed plan, so that wording should describe an intended change until the diff and negative authorization tests prove it. The same distinction applies to headings calling every hypothesis a production root cause.
