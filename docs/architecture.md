# conn3ct — Architecture Document

## 1) Architecture Goals

- Support large-scale sessions with predictable costs and good UX
- Separate “product API” from “real-time media” concerns
- Use horizontally scalable components (stateless where possible)
- Provide secure recording delivery with optional Paystack paywall

## 2) Key Assumption About “10,000 Users in a Meeting”

Supporting 10,000 participants in a single session is feasible only with a **webinar-first model**:

- A small number of publishers (hosts/presenters) send audio/video
- A large number of viewers receive streams (often video off or low bitrate)
- Features like Q\&A/chat are handled via scalable messaging, not media

For “true 10,000-way interactive video” (everyone sending video), costs and SFU limits grow dramatically; conn3ct should enforce plan-based caps and modes to remain reliable.

## 3) High-Level Components

Product side:

- **Web App**: dashboard + join pages + recording pages
- **Native Clients**: Desktop (Windows/macOS/Ubuntu) and Mobile (iOS/Android) apps containing custom media engines to bypass browser WebRTC hardware limitations.
- **API Service**: auth, teams, rooms, recordings, billing, invites
- **Email Service**: transactional messages (invites, password resets)
- **Payment Service** (part of API): Paystack initialize + webhook processing
- **Database**: Postgres (recommended), with read replicas as needed
- **Cache/Queue**: Redis for rate limiting, sessions, job queues

Real-time side:

- **Signaling Gateway**: WebSocket service for room join, role updates, chat/Q\&A events
- **SFU Cluster (mediasoup)**: handles WebRTC media routing
- **TURN/STUN (coturn)**: connectivity fallback for NAT/firewalls
- **Recording Pipeline**: captures streams and produces recording artifacts
- **Object Storage + CDN**: stores and serves recordings

Optional/extended:

- **FreeSWITCH (Telephony Gateway)**: SIP/PSTN bridging, IVR, call-in/out, and interoperability.
  - SIP trunk providers (DID numbers, inbound/outbound)
  - IVR flows (DTMF menus, routing, PIN entry, announcements)
  - SIP interoperability (SIP endpoints, PBX integrations)
  - Media bridging to WebRTC via a gateway layer (see Section 10)

## 4) Data Flow (End-to-End)

### 4.1 Join Flow

1. Client requests join token from API: POST /rooms/:roomId/join-token
2. Client connects to Signaling Gateway (WS) using join token
3. Signaling assigns role (host/presenter/audience) and room state
4. Client negotiates WebRTC transports with mediasoup SFU

### 4.2 Media Flow (mediasoup)

- Publishers send audio/video to SFU (DTLS/SRTP)
- SFU forwards to subscribers based on:
  - mode (meeting vs webinar)
  - role (presenters vs audience)
  - bandwidth estimation and simulcast layers

### 4.3 Recording Flow

Options (choose based on quality/cost):

1. **Server-side recording from SFU**: a recording worker joins as a “listener” and records selected streams.
2. **Client-side recording** (not recommended for reliability): host records locally and uploads.

Preferred approach:

- Use server-side recording workers per session
- Output MP4/HLS, upload to object storage
- Publish recording record in DB with URL + paywall flags

### 4.4 Recording Playback + Paywall

1. User opens recording link
2. Web/API checks:
   - free vs paid
   - membership/ownership
   - verified payment transaction
3. If paid and not verified:
   - initialize Paystack transaction
   - redirect to Paystack or embed checkout
4. On successful payment:
   - webhook verifies transaction
   - grant access (store transaction, mark verified)
5. Playback served via CDN with access control strategy (below)

## 5) Recording Access Control Options

Recommended layered approach:

- Public recording page can be accessible
- Actual media URL should be protected via one of:
  - **Signed URLs** (time-limited) generated by API
  - **Token-gated proxy** endpoint that streams from storage/CDN

Minimum requirement:

- Never expose “permanent private storage URLs” for paid content

## 6) Scaling Strategy

### 6.1 API and Dashboard

- API is stateless; scale horizontally behind a load balancer
- Redis for shared state: sessions, rate limits, background jobs
- Postgres with proper indexing, connection pooling, read replicas if needed

### 6.2 Signaling

- WebSocket gateway scales horizontally with sticky sessions OR shared state in Redis
- Room presence stored in Redis (or dedicated presence service)
- Rate-limit join/leave storms

### 6.3 SFU (mediasoup) Scaling

Pattern:

- Each SFU node hosts multiple “routers” (rooms) depending on CPU/bandwidth
- Use a **Room Allocator** service that assigns new rooms to an SFU node based on load
- Keep room media on one SFU node when possible for simplicity

For very large webinars:

- Prefer **few publishers** + many subscribers
- Use simulcast + SVC where supported
- Consider audience defaults:
  - video off by default
  - auto-subscribe only to active speakers

Advanced (for extreme scale):

- **Cascading SFUs** (regional edge SFUs subscribe to a parent SFU) to reduce long-haul traffic and expand fanout
- “Stage” model: presenters connect to core SFU; viewers connect to nearest edge SFU

### 6.4 TURN

- Operate multiple TURN nodes geographically
- Monitor TURN usage (it can become a major bandwidth cost)

### 6.5 Bandwidth Optimization (Live Media)

Client + SFU strategies (use together):

- **Simulcast / SVC**: publishers send multiple layers; subscribers receive only what they can decode and what the UI needs.
- **Dynamic subscription**:
  - Webinar: audience subscribes only to stage presenters
  - Meeting: subscribe to active speaker(s) + pinned tiles; pause others
- **Bandwidth caps by role**: stricter caps for audience; higher caps for presenters.
- **Adaptive video policies**:
  - Default audience video off; allow opt-in
  - Lower default resolution (e.g., 360p/480p) for large webinars
  - Disable HD unless explicitly requested and capacity allows
- **Audio optimizations**: Opus with DTX; prioritize audio over video under congestion.
- **Congestion control**: transport-wide CC feedback (TWCC) and sender-side bitrate adaptation.
- **TURN avoidance**: improve direct connectivity with proper ICE/STUN configuration; TURN only as fallback.

### 6.6 Auto-Scaling Plan (Example: 20 Concurrent Webinars)

Key constraint:

- A live room cannot be “moved” between SFU nodes mid-session without disruption; scaling is done by allocating rooms to available capacity at start and maintaining headroom.

Recommended design:

- **Capacity model**: define “capacity units” per SFU node (CPU + egress bandwidth). Track real-time usage:
  - active routers/rooms
  - publishers and subscribers
  - egress bitrate and packet rate
  - TURN-relayed traffic
- **Room Allocator**:
  - Assign each new webinar to an SFU node with sufficient spare capacity
  - Enforce plan-based caps (max concurrent webinars, max audience size, max presenters)
  - Keep a safety headroom percentage to avoid overload spikes
- **Separate node pools**:
  - Webinar SFU pool (high egress)
  - Meeting SFU pool (more publishers, different CPU profile)
  - Recording worker pool (CPU/storage intensive)
  - TURN pool (network heavy, cost monitored)
- **Horizontal autoscaling**:
  - SFU pods scale via HPA using custom metrics (egress bitrate, packet rate, active routers)
  - Cluster autoscaler adds/removes Kubernetes nodes for SFU pools based on pending pods and utilization
  - Pre-warm minimum SFU capacity before scheduled peak times (cron-based scale-up)
- **Regionalization**:
  - Allocate webinars to the nearest region to most attendees when possible
  - Use cascading SFUs for global audiences when a single region causes long-haul egress
- **Admission control**:
  - If capacity is exhausted, degrade gracefully:
    - reduce default video layers (audio-first)
    - limit stage video tiles
    - optionally queue late-joiners or redirect to “audio-only” mode
- **Operational approach for “20 webinars”**:
  - Room Allocator places each webinar on an SFU node/router sized for expected audience
  - As webinars start, autoscaling increases SFU replica counts and underlying nodes
  - Continuous metrics prevent saturation; new webinars are routed to new nodes as they appear

### 6.7 Zoom-Class Enterprise Upgrades (Global Footprint + Hybrid Edge)

This section upgrades conn3ct’s architecture to compete at “Zoom-class” enterprise expectations (global performance, reliability, bandwidth efficiency in campuses, and governance).

Global topology:

- **Multi-region active-active** deployment for API + signaling:
  - Region-local entry points with geo routing
  - Regional isolation: a region failure should not take down the entire product
- **Meeting Zones** concept:
  - Each region contains multiple “zones” (capacity pools) for SFU + TURN + recording workers
  - New rooms/webinars are assigned to a zone based on latency + capacity

Enterprise bandwidth reduction (campus/enterprise networks):

- **Conn3ct Edge (optional on-prem/hybrid module)**:
  - A customer-deployed edge SFU/iMMR that redistributes meeting media locally for users inside the same network, reducing external bandwidth consumption.
  - Cloud control plane remains authoritative for scheduling, identity, and policies; media can stay local when the meeting is internal-only or when only internal participants are present.
  - This mirrors the “hybrid SFU/iMMR” approach used in enterprise hybrid meeting products (reference: Zoom Meetings Hybrid explainer).

Media routing upgrades:

- **Global rendezvous + regional media selection**:
  - Client pings candidate regions/edges and selects lowest-latency viable entry point.
  - Sticky placement per meeting: keep a meeting anchored to its chosen media region/zone for stability.
- **Cascaded SFU fanout for extreme webinars**:
  - Core SFU receives presenter streams; edge SFUs subscribe and redistribute to local audiences.
  - Reduces long-haul egress and improves latency for globally distributed attendees.

Reliability upgrades:

- **N+1 capacity policy** per region/zone for SFU and TURN pools.
- **Graceful degradation ladder**:
  - limit video tiles → reduce layers → audio-only → queue/deny late joiners (plan-based).
- **Automated failover behaviors**:
  - If a local edge module fails, clients fail back to cloud media when possible.
  - If a regional SFU pool is saturated, allocator spills to the next-best region (with policy controls).

Security/governance upgrades:

- **Enterprise identity**: SSO (SAML/OIDC), SCIM provisioning, enforced MFA, conditional access (roadmap to MVP+).
- **Key management options**:
  - Support a customer-managed key mode for regulated customers (architecture-level requirement).
  - Note: true end-to-end encryption and PSTN/SIP interoperability have inherent trade-offs; define policy per meeting mode.
- **Auditability**:
  - Immutable audit logs for admin actions, recording access, telephony call-outs, and payment events.

Operational excellence:

- **Global observability**:
  - Per-meeting QoE metrics (packet loss, RTT, jitter, bitrate) and per-node saturation signals.
  - Cost telemetry: TURN relay % and egress per meeting, per tenant, per plan.
- **Progressive delivery**:
  - canary + rollback for signaling, allocator, and SFU worker releases.

Reference (public):

- Zoom Meetings Hybrid Explainer (hybrid SFU/iMMR concept and bandwidth reduction approach): <https://library.zoom.com/advanced-enterprise-services/zoom-node/zoom-meetings-hybrid/zoom-meetings-hybrid-explainer>

## 7) Reliability, SLOs, and Observability

Suggested SLOs:

- API availability: 99.9%+
- Join success rate: 99%+
- Median signaling connect time: < 2s (target)
- Packet loss and RTT monitoring for QoE

Observability:

- Structured logs (requestId, userId, roomId)
- Metrics: CPU, bandwidth, active rooms, publishers, subscribers, TURN relays
- Tracing across API → signaling → SFU allocation

## 8) Deployment Topology (Recommended)

- Kubernetes (or equivalent) with separate node pools:
  - API pods
  - Signaling pods
  - SFU pods (CPU/network optimized)
  - Recording workers (CPU optimized)
- Managed Postgres
- Redis cluster
- Object storage + CDN

Enterprise topology additions:

- Multi-region deployments with geo routing and per-region capacity pools (“meeting zones”)
- Optional Conn3ct Edge modules for customers who need local media routing and bandwidth reduction

## 9) Security Architecture

- Separate public web/app from internal service networks
- Webhook endpoint isolated and signature-verified
- Secrets managed via secret store (KMS/Vault)
- Network policies to restrict SFU/control plane access

## 10) Technology Choices: mediasoup vs FreeSWITCH

- **mediasoup**: best fit for WebRTC SFU, large-scale webinars, modern browser clients.
- **FreeSWITCH**: best fit for SIP/PSTN, telephony features, bridging; use only if those are required.

Recommended:

- Use mediasoup + coturn for core meetings/webinars
- Use FreeSWITCH for SIP/PSTN + IVR + interoperability, integrated through a telephony gateway layer:
  - Inbound PSTN/SIP calls land in FreeSWITCH
  - FreeSWITCH runs IVR (DTMF) and routes calls into a specific room/session
  - A bridging service connects FreeSWITCH media to the WebRTC room (architecture decision: gateway vs direct interop, based on operational constraints)
